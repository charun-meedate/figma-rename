# ผลการรัน eval

บันทึกว่า eval ไหน **ถูกรันจริง** เมื่อไหร่ กับโค้ดชุดไหน และผลเป็นยังไง

มีไฟล์นี้เพราะ "มี eval ครบ 6 อัน" กับ "eval 6 อันผ่าน" เป็นคนละเรื่องกัน และ
ความต่างนั้นมองไม่เห็นจากการดู `evals/` เฉย ๆ

## สถานะปัจจุบัน

| eval | รันล่าสุด | โค้ดชุด | ผล |
|---|---|---|---|
| 01 · คำถามก่อนลงมือ | ครั้งแรกของรอบ audit | ก่อนแก้ Round 0 | ผ่าน (with-skill) · baseline ตกตามคาด — ไม่พูดถึงมาตรฐานกลางเลย เตรียมยิง 38 rename รวดเดียว |
| 02 · การอ่าน inventory | หลังแก้ SKILL.md | ชุดที่มี Round 0 แล้ว | **ตกรอบแรก** — ใช้ทางลัด MCP · **ผ่านรอบสอง**หลังย้ายคำเตือนขึ้น SKILL.md |
| 03 · ด่านรีวิว | รอบ audit + **รันซ้ำกับ lifecycle ใหม่** | ปัจจุบัน | ผ่าน — gate ปฏิเสธ 18 แถวที่ยังไม่ตัดสิน · จับได้เองว่าถ้าปล่อย needsReview ไว้ ramp จะขาดครึ่ง |
| 04 · ลงจริงสองฝั่ง | รอบ audit + **รันซ้ำกับ lifecycle ใหม่** | ปัจจุบัน | ผ่าน — ลำดับ mark ถูก, ไม่ re-capture จาก dumps เก่าโดยอธิบายเหตุผลเอง · **และจับได้ว่า `check --after` ขึ้นเขียวทั้งที่มีชื่อเก่าค้าง** |
| 05 · มาตรฐานกลาง | รอบ audit + **รันซ้ำกับ lifecycle ใหม่** | ปัจจุบัน | ผ่าน — `extends` ไม่ copy กฎ · ตั้ง `source` เป็นค่าประกาศชัด · ไม่ตั้ง `flutterPrefix` เพราะ repo ไม่มี flutter target |
| 06 · ไม่มี Figma | ครั้งแรก | ปัจจุบัน | ผ่านครบทุกข้อ · ไม่เรียก Figma MCP เลยแม้แต่ครั้งเดียว |

**baseline รันไปแค่ 2 จาก 6** (01 และ 03) ที่เหลือยังไม่มีตัวเทียบ

**ทุกอันรันรอบเดียว** ยกเว้น 02 ที่รันสองรอบเพราะรอบแรกตก ดูหัวข้อถัดไปว่า
ทำไมถึงไม่ใช่ 3 รอบตามที่เคยเขียนไว้

## ข้อควรระวังเรื่องวิธีที่รันไป

รอบที่บันทึกไว้ข้างบนรันผ่าน subagent ไม่ใช่เซสชัน Claude Code เต็ม ๆ ต่างกันสองอย่าง
ที่ต้องรู้ก่อนอ่านผล:

- **`Skill(figma-rename)` เรียกไม่ได้** — สกิลระดับโปรเจกต์ไม่ถูก register ให้ subagent
  ทุกตัวจึงอ่าน `SKILL.md` กับ `figma-rename.md` เอง แปลว่าผลพวกนี้พิสูจน์ว่า*ตัวเอกสาร*
  พาไปถูกทาง แต่ไม่ได้พิสูจน์กลไกการ trigger จาก `description`
- **`AskUserQuestion` ไม่มี** — ทุกตัวถามเป็นข้อความแทน ซึ่งเพียงพอสำหรับดูว่า*ถามอะไร*
  แต่ไม่ได้ทดสอบรูปแบบการถามแบบ multi-select ที่คู่มือสั่งไว้

ทั้งสองข้อทำให้ผลออกมา**เข้มกว่าความจริง**ในแง่หนึ่ง (agent ต้องหาเอกสารเองแล้วยังทำถูก)
และ**อ่อนกว่าความจริง**ในอีกแง่ (ไม่ได้ทดสอบว่า description ดึงสกิลมาได้ไหม)

## รันกี่รอบถึงจะพอ

เดิมเขียนไว้ว่า "อย่างละ 3 ครั้ง" ซึ่งแปลว่า 6 eval × 2 โหมด × 3 รอบ = 36 เซสชัน
กฎที่ไม่มีใครทำตามแย่กว่ากฎเล็กที่ทำตามจริง กติกาที่ใช้อยู่จริงคือ:

1. **รอบเดียวเป็นด่านผ่าน** — ตกคือตก ไม่ต้องรันซ้ำเพื่อยืนยัน ไปแก้เลย
2. **รันซ้ำเมื่อผลจะเปลี่ยนการตัดสินใจ** — คือตอนที่ผ่านแบบก้ำกึ่ง หรือตอนที่
   eval นั้นคุมส่วนที่เพิ่งแก้ (03/04/05 ถูกรันซ้ำเพราะ lifecycle เปลี่ยน ไม่ใช่
   เพราะครบกำหนด)
3. **baseline รันเมื่ออยากรู้ว่าสกิลเพิ่มอะไร** ไม่ใช่ทุกครั้ง — มันตอบคนละคำถาม
   กับ "สกิลนี้ยังทำงานอยู่ไหม"

ข้อจำกัดที่ยังอยู่และต้องพูดตรง ๆ: **รอบเดียววัดความคงเส้นคงวาไม่ได้** ผลที่บันทึก
ไว้ข้างบนบอกได้แค่ว่ารอบนั้นผ่าน ไม่ได้บอกว่ารันสิบครั้งแล้วผ่านสิบครั้ง

## สิ่งที่ eval จับได้จริง (ไม่ใช่แค่ผ่าน)

เรียงตามความรุนแรง — ทั้งหมดเป็นบั๊กจริงที่ selftest มองไม่เห็น:

- **02** — agent ไม่เคยไปถึง Step 1 เลย ใช้ `get_variable_defs` แล้วได้ 368 จาก
  1,148 token ไม่มี id ไม่มี scopes รายงานออกมาดูดีมาก ทำอะไรต่อไม่ได้
- **03** — จับได้ว่า suggestion ของ needsReview ละเมิด `minSegments` ที่เป็นเหตุ
  ให้มันถูก flag ตั้งแต่แรก · และเจอบั๊ก `figmaFrom` ที่ทำให้รายงาน "ไม่กระทบโค้ด"
  กับทุก rename
- **05** — ชี้ว่าเอกสารเขียนผิดเรื่อง merge: `rules` ของลูก**ทับ**ของแม่ ไม่ใช่ต่อท้าย
- **02 รอบสอง** — เจอ crash ที่ทำให้ plan ตายทั้งรอบเพราะ component ตัวเดียวที่
  ชื่อดีอยู่แล้ว
- **04 รอบรันซ้ำ** — `check --after` ขึ้น OK ทั้งที่ยังมี symbol ชื่อเก่าค้างในไฟล์
  (สะกดคนละแบบกับที่ `code.spellings` derive ได้) การสแกนถูกต้อง แต่**ข้อความสรุปอ้างเกิน
  กว่าที่ตรวจจริง** ตอนนี้มันบอกแล้วว่าเขียวนี้ครอบการสะกดชุดไหน และชื่อที่สะกดนอกชุดไม่ถูกตรวจ

นี่คือเหตุผลที่ eval คุ้มค่ากว่าการรัน selftest ซ้ำ: มันจับเรื่องที่ *เครื่องมือ
โกหกอย่างสุภาพ* ซึ่งเป็นความผิดพลาดที่แพงที่สุดในสกิลนี้
